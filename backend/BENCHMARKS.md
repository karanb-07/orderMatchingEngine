# Benchmarks

Latency and throughput of the matching core (`MatchingEngine`), measured directly.
No Spring, HTTP, or JSON in the measured path.

## How to run

From `backend/`:

```bash
# Per-operation latency percentiles (prints a Markdown table, ~1-2 min)
./mvnw test-compile exec:exec@latency

# Throughput with JMH (~10 min; results also in target/jmh-result.json)
./mvnw test-compile exec:exec@jmh
```

Close other apps and keep the laptop plugged in while running.

## Workload

Generated by `Workload.java` with a fixed seed (42), so every run sees the same order flow.

- Mid price 100.00, tick 0.01, 50 price levels per side
- Book is pre-filled (untimed) to a target number of resting orders, then held near that depth
- Measured flow: ~54% passive limit adds, ~31% cancels of a random live order, ~15% aggressive orders
- Aggressive orders are sized to never exceed resting liquidity, so they fill completely and never rest
- Tested at 1,000 / 10,000 / 100,000 resting orders (~10 / 100 / 1,000 orders per price level)

## Method

- **Latency:** `LatencyReport.java` replays the stream 5 times to warm up the JIT, then times every order
  individually with `System.nanoTime()` and records into HdrHistogram per operation type.
  Each sample includes ~20 ns of timer overhead. Full distributions are written to `target/latency/*.hgrm`.
- **Throughput:** `MatchingEngineBenchmark.java` (JMH, single-shot mode, 10 warmup + 20 measured invocations,
  2 forks). Each invocation replays 500,000 orders against a freshly built book. Score is ns per order;
  throughput = 1e9 / score.
- JVM flags: `-Xms2g -Xmx2g -XX:+AlwaysPreTouch`. GC log: `target/latency-gc.log`.
- Single-threaded.
