# Benchmarks

Latency of the matching core (`MatchingEngine`), measured directly with no Spring, HTTP, or JSON in the measured path.

**Headline:** replacing `LinkedList` with an intrusive doubly linked list cut cancel p99 at 100k resting orders from **84.4 µs to 1.0 µs (~84×)**, with identical matching behavior.

## How to run

From `backend/`:

```bash
./mvnw test-compile exec:exec@latency   # per-operation percentiles (~15 s)
./mvnw test-compile exec:exec@jmh       # throughput via JMH (~10 min)
```

## Environment

- CPU: Intel Core Ultra 9 285H, 16 logical CPUs
- JVM: Java HotSpot 22.0.2, `-Xms2g -Xmx2g -XX:+AlwaysPreTouch`
- OS: Windows 11
- Single-threaded

## Workload

Generated by `Workload.java` with a fixed seed (42), so every run sees the same order stream.

- Mid price 100.00, tick 0.01, 50 price levels per side
- Book pre-filled (untimed) to 1k / 10k / 100k resting orders, then held near that depth
- 2,000,000 measured orders: ~54% passive limit adds, ~31% cancels of a random live order, ~15% aggressive orders
- Aggressive orders are sized to never exceed resting liquidity, so they always fully fill

## Method

`LatencyReport.java` replays the stream 5 times to warm up the JIT, then times every order individually with `System.nanoTime()` and records it into an HdrHistogram per operation type.

Note: Windows `nanoTime()` has ~100 ns resolution, so sub-microsecond values are quantized to 100 ns steps. Each sample also includes ~20 ns of timer overhead.

## The optimization

**Problem.** Each price level was a `java.util.LinkedList<Order>`. Cancelling an order called `LinkedList.remove(Object)`, which walks the list from the head to find the order: O(n) in queue depth. The cost grew faster than linear because walking scattered nodes causes cache misses.

**Fix.** Each price level is now a `PriceLevel`, an intrusive doubly linked list where `prev`/`next` live on `Order` itself. The existing `orderMap` (order ID → `Order`) returns the node directly, and unlinking it is 4 pointer updates: O(1), no search.

**Correctness.** Both runs produced the same checksum (`sink=24615960`, total fills + successful cancels) on the same 2M-order stream, so matching behavior is unchanged.

## Full results after the fix (100k depth)

| Operation | p50 | p90 | p99 | p99.9 | p99.99 |
|---|---:|---:|---:|---:|---:|
| Add limit (rests) | 100 ns | 300 ns | 500 ns | 700 ns | 3.80 µs |

## Remaining observations

- **Cancel is O(1) but not flat:** 100 ns at 1k depth vs. 600 ns at 100k. The operation count is constant, but at 100k orders the touched data (map bucket, order, neighbors) no longer fits in CPU cache, so each step costs a memory access.
- **Max latencies (up to ~35 ms) are outliers** from GC pauses and OS scheduling, not the matching logic. A per-order `Order`/`Trade` allocation and the ever-growing `trades` list create GC pressure. Possible next steps: object pooling, bounding the trade history.
